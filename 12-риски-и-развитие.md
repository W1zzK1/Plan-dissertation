# 12. Риски и развитие

## Основные риски

| Риск | Вероятность | Влияние | Мера снижения |
|---|---|---|---|
| Реальные данные расписания недоступны для прототипа | Средняя | Высокое | Заглушки, контрактные тесты, адаптер расписания |
| Операционный процесс вокзальной приемки отличается от схемы | Высокая | Среднее | Отдельно фиксировать допущения и проводить интервью с операторами |
| Cutoff приема к погрузке выбран неверно | Средняя | Высокое | Хранить cutoff как настройку рейса, проверять на пилоте |
| Слишком раннее дробление на микросервисы усложнит MVP | Средняя | Высокое | Модульный монолит и ADR о переносе микросервисов |
| Повторы событий создают неверную историю | Средняя | Высокое | Idempotency keys, unique constraints, tests |
| Пользователи создают заявки и не сдают отправления | Средняя | Среднее | Автоотмена через 24 часа и временное ограничение при повторениях |
| Фото отказов и претензий содержат персональные данные | Средняя | Высокое | Приватное хранилище, роли, сроки хранения, маскирование логов |
| Клиент не доверяет статусам при задержках рейса | Средняя | Среднее | Подробная история, уведомления, понятные причины задержек |

## Ограничения MVP

- Поддерживается только направление Москва - Санкт-Петербург и обратное.
- Прием и выдача выполняются только в вокзальных пунктах.
- Интеграции могут быть заменены заглушками.
- Внешние ПВЗ, постаматы вне вокзала и курьерская доставка не входят.
- B2B-грузы, договорная работа и специализированный подвижной состав не входят.
- Точные тарифы, габариты и юридические регламенты требуют отдельного согласования.
- Высокая доступность и георезервирование не проектируются детально для учебного MVP.

## Технический долг, допустимый в MVP

| Долг | Почему допустим | Когда закрывать |
|---|---|---|
| Заглушки расписания и расчета условий | Реальные API могут быть недоступны | Перед пилотом с владельцами внешних систем |
| Один backend вместо микросервисов | Снижает сложность старта | При независимом масштабировании модулей |
| Упрощенная модель расчета стоимости | Не является главным архитектурным риском MVP | После согласования тарифов |
| Упрощенный претензионный контур | Для MVP достаточно открыть, рассмотреть и закрыть претензию | Перед промышленной эксплуатацией |
| Ограниченная панель аналитики | Важнее сначала обеспечить операционный контроль | После первых тестовых перевозок |

## Дорожная карта развития

```mermaid
flowchart LR
    MVP[Вокзальный MVP] --> Pilot[Пилот Москва - Санкт-Петербург]
    Pilot --> StationScale[Масштабирование вокзальных пунктов]
    StationScale --> Partners[Интеграции с ПВЗ, постаматами и курьерами]
    Partners --> Services[Выделение сервисов при необходимости]
    Services --> B2B[B2B-грузы и распределительные центры]
```

## Решения для пересмотра

| Решение | Когда пересмотреть | Что смотреть |
|---|---|---|
| Вокзальный MVP без последней мили | После успешного пилота и появления спроса на доставку до двери или ПВЗ | Доля клиентов, которым неудобна вокзальная выдача, стоимость интеграций |
| Модульный монолит | Модули меняются и масштабируются независимо | Частота релизов, нагрузка, инциденты |
| PostgreSQL как единый источник истины | Появляются очень большие объемы событий | Размер таблиц, скорость запросов, архивирование |
| RabbitMQ | Требуется долговременный поток событий и аналитика | Требования к stream processing и хранению событий |
| Заглушки внешних систем | Появились реальные API расписания и расчета | Контракты, безопасность, SLA |
| Ограничение на мелкие отправления | MVP подтвердил спрос | Требования B2B и инфраструктуры распределительных центров |

## Открытые вопросы

- Кто юридически отвечает за отправление на каждом этапе физической передачи?
- Какой cutoff приема к погрузке реалистичен для вокзального процесса?
- Какие каналы уведомлений обязательны для пилота?
- Какие данные и материалы претензий можно хранить и как долго?
- Какие ограничения по весу, габаритам и содержимому будут утверждены перевозчиком?
