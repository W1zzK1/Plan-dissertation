# 0001. Использовать модульный монолит для MVP

## Статус

Принято.

## Контекст

MVP должен показать сквозной вокзальный цикл мелкого отправления: заявка, приемка на вокзале, назначение рейса по расписанию, перевозка, вокзальная выдача, уведомления и претензии. На этапе курсовой и прототипа важнее быстро собрать целостную модель и проверить сценарии, чем эксплуатировать множество сервисов.

## Решение

Backend MVP реализуется как модульный монолит с четкими внутренними модулями: заявки, вокзальная приемка, назначение рейса, статусы, вокзальная выдача, уведомления, претензии и адаптеры интеграций.

Фоновые обработчики могут запускаться отдельным процессом worker, но используют тот же код доменной модели и те же правила переходов состояния.

## Альтернативы

| Альтернатива | Причина отказа |
|---|---|
| Микросервисы с первого дня | Слишком высокая эксплуатационная сложность для MVP |
| Один неструктурированный монолит | Быстро начнет смешивать доменную логику, интеграции и интерфейсы |
| Только low-code прототип | Недостаточно для архитектурной курсовой и будущей разработки |

## Последствия

- Разработка и отладка MVP проще.
- Транзакционные изменения состояния легче контролировать.
- Нужно дисциплинированно держать границы модулей.
- При росте нагрузки отдельные модули можно выделять постепенно.

## Когда пересмотреть

Решение нужно пересмотреть, если отдельные модули начнут масштабироваться независимо, выпускаться разными командами или мешать друг другу по нагрузке и отказам.
