# 0003. Хранить статусы как доменные события

## Статус

Принято.

## Контекст

Для отправителя, получателя, оператора и поддержки важно понимать, что происходило с отправлением. Простого текущего статуса недостаточно: нужны причины отказов, время переходов, источник события и связь с внешними системами.

## Решение

Хранить текущий статус в сущности `Shipment`, а историю переходов - в `StatusEvent`. Каждый переход создается доменной командой и проверяется state machine. Внешние события применяются идемпотентно по `external_event_id`.

## Альтернативы

| Альтернатива | Причина отказа |
|---|---|
| Хранить только текущий статус | Нельзя восстановить историю и разбирать инциденты |
| Полный event sourcing для всех сущностей | Слишком сложно для MVP |
| Логировать статусы только в технические логи | Логи не являются надежной бизнес-историей |

## Последствия

- У поддержки есть понятная история отправления.
- Повторы внешних событий можно безопасно отбрасывать.
- Модель данных становится чуть сложнее, потому что нужно хранить текущий статус и события.

## Когда пересмотреть

Решение можно расширить до более строгой событийной модели, если появятся сложные требования к аудиту, компенсациям или аналитике.
