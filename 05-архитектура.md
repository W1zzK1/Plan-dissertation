# 05. Архитектура

## Архитектурный стиль

MVP строится как модульный монолит: один backend-код с четкими внутренними модулями, общая база данных, отдельные фоновые обработчики и очередь заданий. Это снижает сложность первой версии, но сохраняет возможность позже выделить отдельные модули в сервисы.

## Контейнерная диаграмма

```mermaid
C4Container
    title Контейнерная диаграмма MVP ИС Экспресс-Л
    Person(sender, "Отправитель", "Оформляет и отслеживает отправление")
    Person(operator, "Оператор", "Приемка, логистика, поддержка")

    System_Boundary(system, "ИС Экспресс-Л") {
        Container(client, "Клиентские каналы", "Web / mobile / bot", "Оформление заявки и просмотр статусов")
        Container(operatorUi, "Панели операторов", "Web", "Приемка, логистика, расследования")
        Container(api, "Backend API", "Модульный монолит", "Команды, запросы, доменные правила")
        Container(worker, "Worker", "Фоновый процесс", "Обработка заданий, интеграций и уведомлений")
        ContainerDb(db, "PostgreSQL", "База данных", "Источник истины по отправлениям и событиям")
        Container(queue, "RabbitMQ", "Очередь", "Асинхронные задания и внешние события")
    }

    System_Ext(trainSystem, "Расписание и движение поездов", "Внешняя система")
    System_Ext(lastMile, "ПВЗ, постаматы, курьеры", "Внешняя система")
    System_Ext(notifications, "Провайдер уведомлений", "SMS, push, bot")
    System_Ext(pricing, "Расчет стоимости", "Внешний или внутренний сервис")

    Rel(sender, client, "Использует")
    Rel(operator, operatorUi, "Использует")
    Rel(client, api, "HTTPS")
    Rel(operatorUi, api, "HTTPS")
    Rel(api, db, "Читает и пишет")
    Rel(api, queue, "Публикует задания")
    Rel(worker, queue, "Получает задания")
    Rel(worker, db, "Обновляет состояние")
    Rel(worker, trainSystem, "Запрашивает расписание и события")
    Rel(worker, lastMile, "Передает на выдачу")
    Rel(worker, notifications, "Отправляет уведомления")
    Rel(api, pricing, "Рассчитывает условия")

    UpdateLayoutConfig($c4ShapeInRow="2", $c4BoundaryInRow="1")
```

## Основные модули backend

| Модуль | Ответственность |
|---|---|
| Identity and Access | Пользователи, роли, проверка владения отправлениями |
| Shipment Application | Создание и валидация заявок |
| Parcel Acceptance | Приемка, физическая проверка, отказ с причиной |
| Routing | Подбор поезда, формирование route plan |
| Shipment Tracking | Статусы, доменные события, история |
| Last Mile | Передача в постамат, ПВЗ или курьерскую службу |
| Notifications | Шаблоны и отправка уведомлений |
| Investigation | Повреждения, задержки, расследования, компенсационное решение |
| Integration Adapters | Контракты и адаптеры внешних систем |

## Компонентная диаграмма ключевого модуля

Ключевым считается модуль управления отправлениями, потому что он связывает заявку, посылку, маршрут, статусы и исключения.

```mermaid
C4Component
    title Компоненты модуля управления отправлениями
    Container_Boundary(api, "Backend API") {
        Component(commandHandlers, "Command handlers", "Код", "Принимают команды пользователей и операторов")
        Component(queryHandlers, "Query handlers", "Код", "Возвращают статусы и историю")
        Component(domainService, "Shipment domain service", "Код", "Проверяет переходы состояния и бизнес-правила")
        Component(statusLog, "Status event service", "Код", "Фиксирует статусные события")
        Component(routePlanner, "Route planner", "Код", "Подбирает поезд и маршрут")
        Component(integrationPorts, "Integration ports", "Интерфейсы", "Изолируют внешние системы")
        Component(repositories, "Repositories", "Код", "Работают с PostgreSQL")
    }

    ContainerDb(db, "PostgreSQL", "База данных", "Отправления, маршруты, события")
    Container(queue, "RabbitMQ", "Очередь", "Фоновые задания")
    System_Ext(external, "Внешние системы", "Расписание, последняя миля, уведомления")

    Rel(commandHandlers, domainService, "Передают команды")
    Rel(queryHandlers, repositories, "Читают данные")
    Rel(domainService, statusLog, "Создает события")
    Rel(domainService, routePlanner, "Запрашивает маршрут")
    Rel(routePlanner, integrationPorts, "Использует порты")
    Rel(statusLog, repositories, "Сохраняет события")
    Rel(repositories, db, "SQL")
    Rel(commandHandlers, queue, "Публикуют задания")
    Rel(integrationPorts, external, "Адаптеры")
```

## Правила зависимостей

- Доменная логика не зависит от конкретных API внешних систем.
- Команды меняют состояние только через domain service.
- Текущее состояние отправления хранится в таблице отправлений, а история - в status events.
- Worker может повторно выполнить задание без повреждения состояния.
- Панели операторов используют тот же API, что и клиентские каналы, но с другими правами.
- Адаптеры внешних систем не должны писать в базу напрямую, только через прикладные команды.

## Ключевые политики

| Политика | Где реализуется | Почему здесь | Как проверить |
|---|---|---|---|
| Проверка владельца отправления | Backend API и domain service | Все пользовательские операции проходят через API | Security tests |
| Валидация переходов статусов | Shipment domain service | Статус нельзя менять произвольно | Unit tests state machine |
| Автоматическая отмена через 24 часа | Worker и domain service | Зависит от времени и состояния | Integration test планировщика |
| Идемпотентность внешних событий | Status event service и PostgreSQL | Повтор события не должен менять историю дважды | Idempotency tests |
| Повторы внешних вызовов | Worker | Сетевые сбои не должны ломать процесс | Failure tests |
