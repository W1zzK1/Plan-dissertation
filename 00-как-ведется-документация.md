# 00. Как ведется документация

## Назначение

Этот набор документов описывает целевую архитектуру MVP, а не окончательную реализацию промышленной системы. Документация нужна для обсуждения решений, выявления рисков, согласования границ проекта и последующей разработки прототипа.

## Правила работы

- Факты, решения, допущения и открытые вопросы фиксируются явно.
- Требования должны иметь способ проверки.
- Названия сущностей, статусов и компонентов используются одинаково во всех разделах.
- Диаграммы Mermaid находятся рядом с текстом, который они поясняют.
- Решения, влияющие на архитектуру, данные, надежность, безопасность, стоимость или сроки, фиксируются в ADR.

## Принятые сокращения

| Сокращение | Значение |
|---|---|
| ВСМ | Высокоскоростная железнодорожная магистраль |
| MVP | Минимальная полезная версия системы |
| ЛНП | Начальник поезда или ответственное лицо поездной бригады |
| ИС | Информационная система |

## Уровень детализации

Документация должна быть достаточно подробной, чтобы по ней можно было:

- объяснить границы MVP;
- нарисовать и защитить архитектуру;
- составить backlog разработки;
- определить набор интеграций;
- оценить риски и ограничения;
- проверить, что ключевые сценарии не потеряны.

Полные промышленные регламенты, юридические договоры, точные тарифы и реальные API партнеров в этой версии не фиксируются. Для них указаны допущения и контракты, которые нужно уточнить перед промышленной реализацией.
